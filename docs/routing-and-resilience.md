# PrismLLM 路由与容灾机制

PrismLLM 设计为高可用单实例网关，专注于在无需复杂微服务和 Redis 等分布式缓存集群的前提下（仅依赖轻量 PostgreSQL 存储持久化数据与审计），实现多渠道流量分摊、故障快速自愈与高压限流保护。

---

## 一、模型聚合与多层级路由调度

### 1. Canonical Model ID 跨渠道聚合
- 渠道在配置模型映射时可指定**对外模型 ID**（规范 ID / Canonical ID）。
- 多个渠道配置相同的对外模型 ID 时，网关会将它们聚合为同一个虚拟模型对外暴露（如在 `/v1/models` 中仅呈现为一个条目）。
- 外部请求以对外模型 ID 进入，网关会在转发至特定上游前自动重写为实际上游模型名。
- **暴露与凭据解耦**：模型只有在渠道启用、且存在至少一条可路由凭据（密钥或订阅账号）时才进入 `/v1/models` 并接受直连请求。渠道的启用开关只表达运营意图，不代表模型一定可用；支持该模型的凭据全部停用后，模型会从列表中消失。
- **不可用与不存在分开表达**：请求一个已配置但凭据全部停用的模型返回 `503 model_credentials_unavailable`（存在临时停用密钥时带 `Retry-After`，取各密钥停用到期与探测租约中较晚者的最早值），只有模型确实未配置时才返回 `404 model_not_found`。这样客户端能区分「配置写错了」和「上游暂时不可用」。凭据不可路由导致的 503 与冷却无关，Fail-Open 兜底仍然成立。

### 2. 优先级分档与同档分摊
路由决策采用分层策略：
1. **渠道优先级**（`priority`）：数值越小优先级越高。流量优先打向最高档位渠道；
2. **同档轮询分摊**：同一优先级档位内的多个可用渠道通过 Round-Robin 算法分摊流量；
3. **密钥优先级**：进入渠道后，优先使用该渠道内优先级最高的一组密钥，同优先级密钥进行轮询。

## 二、上游分组主动限流

为避免将上游渠道打垮或因超出配额产生高额罚款，PrismLLM 支持在渠道密钥级别配置本地主动限流：

- **RPM 令牌桶**：使用平滑令牌桶算法，独立统计每个密钥的每分钟请求上限；
- **最大并发请求数**：请求发送至上游时占用配额，直到响应结束、客户端主动断开或超时后释放；
- **限流回退**：本地被限流拒绝时，网关会优先尝试同一模型的备用密钥或备用渠道，只有全部候选均繁忙时才返回 `429 upstream_key_rate_limit_exceeded` 及 `Retry-After` 响应头，且不会计入故障冷却。
- **实时占用**：管理台渠道列表展示每个渠道及其密钥的当前在途请求数，调用方密钥列表展示每个密钥的实时并发；计数覆盖未配置并发上限的密钥，只用于展示，不改变限流判定。

## 三、上游密钥自动停用（Key Auto-Disable）

管理台的「上游接入点 → 密钥自动禁用」支持配置全局规则，规则按顺序匹配，首条命中生效。

渠道可以覆盖全局规则：在渠道操作菜单选择「密钥自动禁用」，三选一——**继承全局**（默认）、**自定义**（渠道规则排在前面，未命中时回落全局规则，仍是首条命中即止）、**关闭**（本渠道的渠道规则和全局规则都不执行）。自定义只保存渠道自己的规则，全局规则更新后自动生效；与全局同 id 的规则由渠道版本接管（可用于收紧某条全局规则）。渠道规则只作用于本渠道的上游密钥，适合承载某个上游特有的错误特征（例如 Grox 的 `DEEPSEEK_ACTIVITY_DISABLED`）。切换形态或修改规则都会让该渠道已累计的失败计数失效，重新计数。

### 1. 四态生命周期模型

| 状态 | 标识 | 产生方式 | 恢复方式 |
| :--- | :--- | :--- | :--- |
| **正常** | `ACTIVE` | 人工启用或系统恢复 | 正常参与直连路由 |
| **人工停用** | `MANUAL_DISABLED` | 管理员手动停用 | 仅管理员手动启用 |
| **临时停用** | `AUTO_TEMPORARY` | 命中临时规则达到阈值 | 带到期时间，到期后单探测自愈 |
| **永久停用** | `AUTO_PERMANENT` | 命中永久规则（如凭据失效） | 绝不自动恢复；管理员人工启用 |

### 2. 临时到期与单探测抢占（Probe Lease）
- 密钥进入 `AUTO_TEMPORARY` 后带到期时间戳；
- 到期后不会并发蜂拥打向上游，而是由先到达的单个请求通过原子操作抢占**单探测租约**（`probe_until`）；
- 探测请求成功，密钥状态完全恢复为 `ACTIVE`；探测失败，重置临时停用时长并重新计时；
- 后台扫描任务会定时收尾已到期且无有效租约的残留密钥。

### 3. 永久停用与人工恢复
- 当命中明确凭据错误（如 `invalid_api_key`）或严重封禁时，密钥被标记为 `AUTO_PERMANENT`；
- 命中永久停用的密钥不会自动恢复；管理员在排查上游问题、更换凭据或充值后，可在控制台直接将其人工重新启用为 `ACTIVE`（保留或替换凭据均可），启用后系统会清空该密钥的历史失败计数与冷却状态。

## 四、候选故障转移与冷却机制（Candidate Cooldown）

当上游发生异常时，网关实施首 Token 前无缝故障转移与基于影响面的差异化冷却：

### 1. 首 Token 前快速转移
- 若上游在输出第一个 Token 前发生连接超时、连接重置、5xx、429、401、403、404、422，或 400 命中形状拒绝词表，网关会立即切换至下一个候选档位，单次请求最多尝试 `MAX_ATTEMPTS` 次；
- **形状拒绝（Shape Refusal）**：422 一律视为上游读不懂请求形状；400 仅在错误文本命中 `failed to deserialize`、`unknown variant/field/parameter`、`additional properties are not allowed`、JSON Schema 嵌套深度、思考内容未回传（`reasoning_content … must be passed back`）、`developer is not one of …` 等词表时才计入。这类错误说明请求与当前上游不兼容，换一个候选可能直接成功，因此会故障转移，但不会让当前渠道进入冷却；缺失必填字段等所有上游都会拒绝的错误不在此列；
- 一旦首 Token 已发送给调用方，由于流式协议无法回滚，后续发生的中断不再切换渠道，直接透传中断信号。

### 2. 差异化影响面冷却（Cooldown）

| 异常类型 | 冷却键范围 | 持续时间 | 机制 |
| :--- | :--- | :--- | :--- |
| **传输层错误与 5xx** | 作用于渠道级别 | `30s` 起步，连续失败翻倍，上限 `10m` | 瞬时错误退避 |
| **429 限流** | 作用于密钥+模型级别 | 默认 `30s`，上限 `60s` | 尊重上游 `Retry-After` 头 |
| **401/403 鉴权失败** | 作用于密钥级别 | 默认 `10m` | 结合自动禁用规则联动处置 |
| **慢流（TTFT 惩罚）** | 作用于密钥+模型级别 | 连续 `3` 次首 Token 超过 `10s` 时触发 | 避免慢节点拖垮整体体验 |

- **Fail-Open 兜底**：若同一模型下的全部可用候选均处于冷却中，网关仍按档位顺序尝试一次请求（Fail-Open），避免全量宕机。
- **管理面可见性**：渠道列表展示冷却候选数、最近恢复时间和主因；渠道健康详情的「当前路由状态」按密钥与模型列出冷却原因和截止时间，并支持按渠道、密钥或候选手动解除。解除动作写入管理操作审计。冷却原因随状态写透 PostgreSQL，重启后仍可展示。
- **请求日志可追溯**：`request_logs.attempts_json` 会为因冷却跳过的候选追加 `skipped=true`、`skipReason=cooldown` 的记录；这些记录不计入 `upstream_attempts` 和渠道健康度。

### 3. 订阅账号级调度（OAuth Account Scheduling）

订阅账号（ChatGPT、Antigravity）是独立的上游凭据，可关联多个渠道；账号级限制由 `OAuthAccountScheduler` 在路由准入阶段执行：

- **滑动窗口**：按账号统计，不区分模型，默认不限制；可在「订阅账号」页为每个账号单独设置窗口请求数与窗口时长；
- **单号并发**：默认 1，超出后跳过该账号并继续尝试其他候选；
- **429 冷却**：优先使用 `Retry-After` 或响应体中的重置提示，没有提示时按连续 429 次数指数退避，单次最长 6 小时；
- **上游额度**：后台每 5 分钟读取一次 ChatGPT 的 `/wham/usage`，记录 5 小时与每周窗口的使用比例、重置时间与 credits；任一窗口用尽且没有 credits 时立即停止调度该账号，不必等到下一次 429。每次上游回复携带的 `x-codex-primary-*` / `x-codex-secondary-*` 响应头也会即时合并进内存读数，按窗口时长对齐并保留 credits 等轮询字段。读数超过有效期（默认 15 分钟）后只展示、不再拦截，避免上游异常导致账号被长期误停；
- **账号排序**：`OAUTH_ROUTING` 选择同一渠道、同一凭据优先级内的账号顺序。默认 `round_robin` 沿用档位轮询；`drain` 固定当前账号直到它额度用尽或进入冷却，再顺延到下一个；`least_used` 按额度读数中的最高已用比例升序；`pace` 按剩余比例摊到距重置的小时数，余量最高者优先。静态密钥与不同优先级档位不受影响，命中 `prompt_cache_key` 亲和时保持亲和顺序；
- **硬限制**：账号级窗口、并发、额度与冷却不进入 Fail-Open；全部候选都被账号级限制拦下时返回 `429 subscription_account_rate_limited`，并带上最早可重试时间；
- **凭据不可用**：`subscription_account_unavailable` 按候选长冷却，`subscription_account_refresh_failed` 按候选短冷却，两者都会继续尝试其他候选；
- **管理面**：订阅账号看板展示授权状态、关联渠道、token 到期时间、上游额度进度、窗口用量与冷却剩余时间，支持新建/删除账号、调整关联渠道与模型、重新授权、手动刷新 token 与额度、编辑调度策略与解除冷却；重新授权会清空账号冷却、各关联渠道下的候选冷却与失败计数。

## 五、渠道健康度被动大盘

网关管理界面根据真实出站请求被动汇总健康度，无需额外的主动心跳流量污染上游：
- **时间窗口**：支持查看 `24h`、`7d`、`15d`、`30d` 的健康表现；
- **核心指标**：单次尝试成功率、重试/切换率、首 Token P50/P95 耗时、平均输出速度；
- **异常判断**：有效样本数少于 20 个或最近一小时内没有样本时显示“未知”；失败率达到 5% 显示“需关注”，达到 20% 显示“异常”；停用渠道显示“已停用”；
- **无可用凭据**：渠道仍启用、但静态密钥与订阅账号里没有任何一条能支持渠道当前模型目录的可路由凭据时显示“无可用凭据”，优先于“未知”判定。该判定只由服务端按完整凭据集给出；报告尚未加载或读取失败时显示“未知”，不用只覆盖静态密钥的本地判定冒充，避免把“账号仍在支撑”的渠道误报为不可用。渠道的启用开关表达运营意图，不代表模型一定可用；两个状态分开显示，避免把“运营者主动关掉”和“想跑但跑不了”混为一谈；
- **明细拆解**：点击渠道可下钻查看按模型、出站协议和具体密钥拆分的成功率与错误原因分布。
- **缓存使用**：展示缓存命中率与缓存读/写、输入 token，并按上游模型拆分各自的命中率（按输入 token 降序），避免不同模型的缓存行为被整体流量摊平；口径与用量报表一致，仅供诊断展示，不参与健康度判定，读取失败不影响健康度统计。按模型拆分的用量来自请求日志，与按上游尝试统计的成功率表口径不同，两者分开展示。

## 六、范围边界

PrismLLM 保持「单实例自托管网关」定位，当前路线图不包含：

- Redis、配置中心或多副本共享状态；
- 渠道/密钥的加权轮换（同档均匀轮询已满足分摊需求）。

冷却、限流与配置读取均由单实例进程内存 + PostgreSQL 完成；本地限流拒绝保持 `429 + Retry-After`，不写入故障冷却。
