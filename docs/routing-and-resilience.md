# PrismLLM 路由与容灾机制

PrismLLM 定位为单实例自托管网关，在 PostgreSQL 持久化配置、额度与观测数据的基础上，实现显式模型凭据路由、候选故障转移与本地限流保护；不把单实例容灾描述为多副本高可用保证，也不依赖 Redis 等分布式协调服务。支持四协议原生透传和 12 个有向跨协议转换方向，转换能力与事件缓冲边界见 [协议转换](protocol-conversion.md)。

---

## 一、Canonical Model ID 与显式模型路由

### 1. Canonical Model ID 跨渠道聚合
- 渠道在配置模型映射时可指定**对外模型 ID**（Canonical ID）。
- 多个渠道配置相同的对外模型 ID 时，网关将它们作为同一个公共模型管理；模型目录中只呈现一个 ID。
- 外部请求以对外模型 ID 进入，转发到选定的渠道凭据时改写为对应的上游模型名。
- **映射、路由与暴露分别判断**：渠道授权模型定义上游映射，模型路由定义可尝试的凭据身份。数据面模型列表只展示已保存路由中仍有可路由凭据支持、符合调用方范围及端点原生协议规则的公共 ID；未配置路由或路由为空时不列出。请求还需通过额度、账号窗口/并发等准入检查。
- **不可用与不存在分开表达**：已配置模型没有任何符合资格的已选凭据时返回 `503 model_credentials_unavailable`；模型未配置仍返回 `404 model_not_found`。显式保存空路由表示没有路由，不会回退到目录中的其他凭据。

#### 调用方密钥访问范围

管理台的调用方密钥创建与编辑表单提供渠道、渠道密钥和对外模型 ID 三个维度，每项可选择不限制、白名单或黑名单并多选，同一维度模式互斥。模型选项只来自已保存的模型路由：没有路由的对外模型 ID 不能新增，路由已保存但没有选中凭据时仍可选择并标记为“暂无可用凭据”。模型行可按需展开生效路由预览，按保存顺序列出渠道、静态密钥或订阅账号，并逐条标注路由自身不可用原因、调用方渠道/密钥范围拒绝原因或“当前范围可用”；预览只读，不改变授权。选项仅包含名称与 ID，静态密钥按 `(channelId, keyId)` 配对，不展示凭据明文。目录按需加载；停用项可以选择，已删除、目录加载失败或路由已消失的选择会明确标记并保留，界面不会自动改变模式。已有模型黑名单 ID 在路由移除后可继续保留并保存其他修改；新增模型 ID 必须已有模型路由。

| 模式 | 含义 |
| --- | --- |
| `unrestricted`（不限制） | 使用当前全局配置中满足其他规则的对象，名单数组为空。 |
| `allowlist`（白名单） | 只允许所列对象，空名单表示该维度无授权目标，整个调用方密钥不能调用模型。 |
| `denylist`（黑名单） | 禁止所列对象，其他对象按其余规则使用；空黑名单不额外限制，新增目标也按其余规则使用。 |

同维度名单可多选，三个维度取交集。例如允许模型 M1、M2 并将渠道 A 加入黑名单时，只能通过其他符合规则的渠道调用这两个模型；本版不提供逐模型访问范围策略。对外模型 ID 精确匹配，不改写大小写、不支持通配符。渠道与静态密钥限制作用在模型路由的候选身份上：命中路由条目但被渠道或密钥范围排除的凭据不会生成候选。静态密钥白名单必须属于渠道允许范围；静态密钥黑名单可排除任何现存 Key，范围外的排除项不额外产生效果。静态密钥白名单排除 OAuth 订阅账号；静态密钥黑名单只排除所选静态 Key，保留 OAuth；渠道黑名单同时排除该渠道的静态 Key 与 OAuth。

管理 API 的 `accessPolicy` 完整对象示例：

```json
{
  "channels": { "mode": "allowlist", "ids": ["channel-a", "channel-b"] },
  "channelKeys": {
    "mode": "allowlist",
    "keys": [{ "channelId": "channel-a", "keyId": "key-1" }]
  },
  "models": { "mode": "allowlist", "ids": ["Model-A"] }
}
```

将上述任一维度的 `mode` 改为 `denylist`，同一份 `ids` 或 `keys` 就表示排除项。例如 `"models": {"mode":"denylist","ids":["Model-A"]}` 禁止所有渠道上的该对外模型。

创建省略 `accessPolicy` 时默认为三个维度均不限制。更新省略该字段或传 `null` 时保留已有授权；提交完整对象时原子替换三个维度。切回不限制模式须显式发送 `unrestricted` 和空数组，不能通过省略字段切换。读响应始终包含完整对象。轮换、启停保留访问范围；撤销后仍不能编辑或轮换。删除目标不改变模式：空白名单仍拒绝全部，空黑名单不额外限制。模型黑名单 ID 在路由移除后保留，重新保存同 ID 路由后仍被禁止；静态对象删除时清理失效关联，新建对象具有新 ID。V69 为旧密钥保留既有不限制/白名单配置。

授权过滤先于上游许可、探测租约和上游调用，普通重试、冷却兜底、协议转换及搜索内部模型调用均只使用授权候选。每次请求共用一份访问范围快照；管理修改对后续请求生效，在途请求继续使用原快照。授权范围外的冷却、可用性或恢复时间不影响本次诊断与 `Retry-After`。

模型已配置但被白名单或黑名单拒绝时返回 `403 model_access_denied`；模型获准但所有支持它的配置路由都被渠道/静态密钥范围排除时返回 `403 route_access_denied`，两者均不尝试上游。两类 403 都包含 `X-Prism-Error-Code` 响应头。OpenAI 错误体同时保留字符串 `error.code`；Messages 与 Gemini 保持原生错误体，客户端通过响应头读取稳定错误码。模型未配置保持 404；授权渠道暂不可用时，仅在范围内返回原有 429、503 或上游错误。静态密钥维度为不限制或黑名单，而授权渠道没有支持该模型的配置凭据时，仍返回 `503 model_credentials_unavailable`；没有凭据与已有凭据全部被名单拒绝分别处理。三个维度均不限制或仅为空黑名单时，实际授权及停用渠道目录口径与原不限制模式一致。

现有 `GET /v1/models` 与 `GET /v1beta/models` 仅展示已保存路由中存在可路由且获授权凭据的公共 ID，保留各自原生协议匹配与响应格式；未选择的其他凭据不会让模型重新进入列表。模型路由管理不会新增数据面模型列表端点。Chat Completions、Responses、Messages 和 Gemini 请求都执行访问范围校验；Gemini 两个版本的生成路径从 URL 读取对外模型 ID，同样不能绕过限制。

### 2. 管理员配置的有序凭据身份

每个模型路由保存有序身份列表，每项由 `channelId`、`credentialType`（`static` / `oauth`）和 `credentialId` 组成。同一 ID 的静态密钥和 OAuth 账号是不同身份。列表顺序就是运行时尝试顺序：管理员可以把协议转换候选排在原生候选之前。一个身份所支持的多个上游模型别名按稳定顺序展开，并保持相邻，不会与其他凭据交错。静态密钥使用渠道协议；OAuth 身份还必须同时满足账号提供方的原生端点协议，实际可用协议为渠道协议与提供方协议的交集。交集为空时保留列表位置但标记不可用，不生成候选，也不曝光对应模型。

- `GET /admin/api/model-routes?q=&offset=&limit=` 返回分页模型摘要；未配置模型显示 `configured=false`、revision `0`。
- `GET /admin/api/model-routes/detail?modelId=` 返回当前已保存 `entries`、全部 `availableCredentials`、revision 和可用性。模型 ID 是公共/Canonical ID；不在路径中，避免斜杠等字符的路径歧义。
- `PUT /admin/api/model-routes` 完整替换路由，只接受 `modelId`、`expectedRevision` 与有序 `entries`。每项只提交上述三个身份字段。版本冲突返回 HTTP 409 `model_route_revision_changed`，应刷新并由管理员核对后重试。

`configured=false`、revision `0` 且没有已保存路由表示尚未配置，运行时没有候选且不会回退到传统候选发现。显式保存 `entries: []` 同样不使用任何凭据，并会保留已配置状态与递增后的 revision。V74 对迁移时启用渠道的活跃公共模型做一次性初始化，只把当时已启用、已授权且符合模型/账号资格的凭据写入初始有序列表；没有合格凭据的模型保留空路由。迁移生成的路由为 `configured=true`、revision `0`，不能仅凭 revision 判断是否配置。初始顺序依迁移时的旧优先级比较生成，此后不再动态排序。之后新增的模型或凭据都不会自动加入既有路由，必须在管理台显式选择。

`channel.priority`、静态密钥和 OAuth 账号的 `priority` 及 OAuth 路由策略环境变量/API 字段为兼容性保留，但不影响运行时路由顺序。管理台保存的完整列表不会因这些字段、协议原生性、`prompt_cache_key` 或策略读数而重排；`prompt_cache_key` 只作为请求字段转发。

### 3. 资格、故障转移与冷却顺序

有序路由规定身份顺序，不会让不符合资格的凭据参加请求。渠道及静态凭据启停、OAuth 授权状态和账号启用状态、模型授权/目录、调用方访问范围、上游额度、账号级窗口与并发限制仍按现有规则筛选。对符合资格的已配置身份，响应提交前发生可重试故障时按列表尝试后续身份；响应提交后不切换。候选冷却会优先尝试列表内未冷却身份；当列表中的候选全部处于冷却时只对同一已配置列表 fail-open，不会加入未选中的凭据。OAuth 账号窗口、并发、额度与账号级冷却仍是硬限制，不进入 fail-open。

## 二、上游分组主动限流

为避免将上游渠道打垮或因超出配额产生高额罚款，PrismLLM 支持在渠道密钥级别配置本地主动限流：

- **RPM 令牌桶**：使用平滑令牌桶算法，按 `channelId + keyId` 独立统计每个密钥的每分钟请求上限，覆盖该密钥的全部模型；计数仅在单实例内存中执行，不跨副本共享；
- **最大并发请求数**：请求发送至上游时占用配额，直到响应结束、客户端主动断开或超时后释放；
- **限流回退**：本地被限流拒绝时，网关继续按该模型已保存路由的顺序尝试其他符合资格且未被限流的身份；不会加入路由之外的密钥或渠道。全部已配置候选均繁忙时返回 `429 upstream_key_rate_limit_exceeded` 及 `Retry-After` 响应头，且不会计入故障冷却。
- **实时占用**：管理台渠道列表仅在当前有在途请求时展示占用提示，零占用收进健康详情；渠道密钥及调用方密钥列表展示每个密钥的实时并发。计数覆盖未配置并发上限的密钥，只用于展示，不改变限流判定。

## 三、上游密钥自动停用（Key Auto-Disable）

管理台的「上游接入点 → 密钥自动禁用」支持配置全局规则，规则按顺序匹配，首条命中生效。

渠道可以覆盖全局规则：在渠道操作菜单选择「密钥自动禁用」，三选一——**继承全局**（默认）、**自定义**（渠道规则排在前面，未命中时回落全局规则，仍是首条命中即止）、**关闭**（本渠道的渠道规则和全局规则都不执行）。自定义只保存渠道自己的规则，全局规则更新后自动生效；与全局同 id 的规则由渠道版本接管（可用于收紧某条全局规则）。渠道规则只作用于本渠道的上游密钥，适合承载某个上游特有的错误特征（例如 Grox 的 `DEEPSEEK_ACTIVITY_DISABLED`）。切换形态或修改规则都会让该渠道已累计的失败计数失效，重新计数。

### 1. 四态生命周期模型

| 状态 | 标识 | 产生方式 | 恢复方式 |
| :--- | :--- | :--- | :--- |
| **正常** | `ACTIVE` | 人工启用或系统恢复 | 正常参与直连路由 |
| **人工停用** | `MANUAL_DISABLED` | 管理员手动停用 | 仅管理员手动启用 |
| **临时停用** | `AUTO_TEMPORARY` | 命中临时规则达到阈值 | 带到期时间，到期后单探测自愈 |
| **永久停用** | `AUTO_PERMANENT` | 命中永久规则（如凭据失效） | 绝不自动恢复；管理员人工启用 |

### 2. 临时到期与单探测抢占（Probe Lease）
- 密钥进入 `AUTO_TEMPORARY` 后带到期时间戳；
- 到期后不会并发蜂拥打向上游，而是由先到达的单个请求通过原子操作抢占**单探测租约**（`probe_until`）；
- 探测请求成功，密钥状态完全恢复为 `ACTIVE`；探测失败，重置临时停用时长并重新计时；
- 后台扫描任务会定时收尾已到期且无有效租约的残留密钥。

### 3. 永久停用与人工恢复
- 当命中明确凭据错误（如 `invalid_api_key`）或严重封禁时，密钥被标记为 `AUTO_PERMANENT`；
- 命中永久停用的密钥不会自动恢复；管理员在排查上游问题、更换凭据或充值后，可在控制台直接将其人工重新启用为 `ACTIVE`（保留或替换凭据均可），启用后系统会清空该密钥的历史失败计数与冷却状态。

## 四、候选故障转移与冷却机制（Candidate Cooldown）

当上游发生异常时，网关在**首数据触发响应提交前**实施候选故障转移，并按影响面执行差异化冷却。这个边界不是第一个有语义的文本 Token；首数据可能是角色、工具、思考或协议生命周期事件，跨协议转换也可能仍在缓冲事件，不能因此推断仍可重试。

### 1. 响应提交前快速转移
- 若上游在响应提交前发生连接超时、连接重置、5xx、429、401、403、404、422，或 400 命中形状拒绝词表，网关可尝试下一个候选，单次请求最多尝试 `MAX_ATTEMPTS` 次；
- **形状拒绝（Shape Refusal）**：422 一律视为上游读不懂请求形状；400 仅在错误文本命中 `failed to deserialize`、`unknown variant/field/parameter`、`additional properties are not allowed`、JSON Schema 嵌套深度、思考内容未回传（`reasoning_content … must be passed back`）、`developer is not one of …` 等词表时才计入。这类错误说明请求与当前上游不兼容，换一个候选可能直接成功，因此会故障转移，但不会让当前渠道进入冷却；缺失必填字段等所有上游都会拒绝的错误不在此列；
- 一旦响应提交，即使调用方尚未收到有语义的文本，后续失败也不再切换渠道或重放响应；按调用方协议报告流式错误或关闭中断流，HTTP 200 不代表流式请求成功。提交前的本地不支持字段/超大事件等不可重试错误不因还有候选就回退。

### 2. 差异化影响面冷却（Cooldown）

| 异常类型 | 冷却键范围 | 持续时间 | 机制 |
| :--- | :--- | :--- | :--- |
| **传输层错误与 5xx** | 作用于渠道级别 | `30s` 起步，连续失败翻倍，上限 `10m` | 瞬时错误退避 |
| **429 限流** | 作用于密钥+模型级别 | 默认 `30s`，上限 `60s` | 尊重上游 `Retry-After` 头 |
| **401/403 鉴权失败** | 作用于密钥级别 | 默认 `10m` | 结合自动禁用规则联动处置 |
| **慢流（TTFT 惩罚）** | 作用于密钥+模型级别 | 连续 `3` 次首数据超过 `10s` 时触发 | 避免慢节点拖垮整体体验 |

- **Fail-Open 兜底**：若同一模型显式路由中的全部符合资格候选均处于冷却中，网关仍按已保存顺序尝试一次请求（Fail-Open），避免冷却启发式导致拒绝服务；不会加入该路由之外的候选。
- **管理面可见性**：渠道列表展示冷却候选数、最近恢复时间和主因；渠道健康详情的「当前路由状态」按密钥与模型列出冷却原因和截止时间，并支持按渠道、密钥或候选手动解除。解除动作写入管理操作审计。冷却原因随状态写透 PostgreSQL，重启后仍可展示。
- **请求日志可追溯**：`request_logs.attempts_json` 会为因冷却跳过的候选追加 `skipped=true`、`skipReason=cooldown` 的记录；这些记录不计入 `upstream_attempts` 和渠道健康度。

### 3. 订阅账号级资格限制（OAuth Account Eligibility）

订阅账号（ChatGPT、Antigravity）是独立的上游凭据，可关联多个渠道；账号级限制由 `OAuthAccountScheduler` 在路由准入阶段执行。窗口、并发、冷却与调度状态以内存为准，部分异步快照只用于重启恢复；OAuth 登录流程和 token 刷新互斥同样只在单实例内有效，不提供跨副本共享调度或刷新锁：

- **滑动窗口**：按账号统计，不区分模型，默认不限制；可在「订阅账号」页为每个账号单独设置窗口请求数与窗口时长；
- **单号并发**：默认 1，超出后跳过该账号并继续尝试其他候选；
- **429 冷却**：优先使用 `Retry-After` 或响应体中的重置提示，没有提示时按连续 429 次数指数退避，单次最长 6 小时；
- **上游额度**：后台每 5 分钟读取一次 ChatGPT 的 `/wham/usage`，记录 5 小时与每周窗口的使用比例、重置时间与 credits；任一窗口用尽且没有 credits 时立即停止调度该账号，不必等到下一次 429。每次上游回复携带的 `x-codex-primary-*` / `x-codex-secondary-*` 响应头也会即时合并进内存读数，按窗口时长对齐并保留 credits 等轮询字段。读数超过有效期（默认 15 分钟）后只展示、不再拦截，避免上游异常导致账号被长期误停；
- **账号排序兼容项**：`OAUTH_ROUTING` 已弃用，仍接受 `round_robin`（默认）、`drain`、`least_used` 与 `pace` 以兼容部署配置，但没有运行时排序效果。OAuth 账号与静态密钥都严格保留模型路由列表顺序；`prompt_cache_key` 仅转发，不进行 HRW/亲和或轮询重排；
- **硬限制**：账号级窗口、并发、额度与冷却不进入 Fail-Open；全部候选都被账号级限制拦下时返回 `429 subscription_account_rate_limited`，并带上最早可重试时间；
- **凭据不可用**：`subscription_account_unavailable` 按候选长冷却，`subscription_account_refresh_failed` 按候选短冷却，两者都会继续尝试其他候选；
- **管理面**：订阅账号看板展示授权状态、关联渠道、token 到期时间、上游额度进度、窗口用量与冷却剩余时间，支持新建/删除账号、调整关联渠道与模型、重新授权、手动刷新 token 与额度、编辑账号级窗口/并发策略与解除冷却；账号优先级和路由策略为兼容性字段，不重排模型路由。重新授权会清空账号冷却、各关联渠道下的候选冷却与失败计数。

### 4. 调用方准入与请求终结

- 调用方 RPM 使用 UTC 固定分钟窗口，并发名额在准入时占用，在完成、失败或取消后的请求终结中释放；两者均只在单实例内有效。
- 每日 Token/USD 额度在准入时检查已结算用量，结束后按 UTC 准入日期结算；跨午夜不改归属，不预留单次最大费用，并发在途请求可使额度超出，因此是软预算。
- 本次请求单次解析价格、计算费用后固定快照，供每日额度账本与异步日志共用；日志消费者不二次算价。额度结算失败记录指标和日志、触发告警，不改变或重放已完成响应，也不重放上游请求。
- 请求日志异步 best effort，可能因队列满、写入失败或强制停机缺失，不是必达财务账本；不承诺 exactly-once 或自动补账。计费与恢复边界见 [计费与用量核算](billing.md)。

## 五、渠道健康度被动大盘

网关管理界面根据真实出站请求被动汇总健康度，无需额外的主动心跳流量污染上游：
- **时间窗口**：支持查看 `24h`、`7d`、`15d`、`30d` 的健康表现；
- **列表双窗口**：近 1 小时状态与 24 小时成功率并列展示，前者独立按近一小时样本判定，不能用全天的成功请求掩盖近期故障。两者都按有效上游尝试统计，客户端取消等排除项不进入分母；近一小时样本不足时仍显示“未知”。
- **列表信息层级**：桌面各列顶部对齐，首行使用统一高度的容器居中对齐，启用开关与渠道名称同一行；模型与其价格来源就近成组，价格来源和“+N”弱化显示，默认最多两项、两行，通过“+N”展开全部。健康列默认仅展示双窗口摘要和近期尝试条，样本量通过悬停提示查看，P95 延迟、实时在途和最近协议探测可在健康详情中查看；更新时间使用相对时间并保留完整时间提示。桌面与手机端的 ID 复制按钮均常驻并固定占位。
- **近期尝试趋势**：列表显示 24 小时内最近 30 次有效上游尝试，由左至右从早到晚；绿色完整柱表示成功，红色短柱表示失败，灰色短线只表示尚无样本、不表示成功。完全没有样本时隐藏趋势条，保留“暂无记录”和健康详情入口；停用渠道只要仍有窗口内历史就继续展示趋势和统计。悬停可查看完成时间、模型、HTTP 状态、错误码及耗时；HTTP 200 后的流式失败仍显示为失败。点击观测区打开原有健康详情；刷新失败时保留上次数据并标明“刷新失败”，首次读取失败不显示为“暂无记录”。
- **核心指标**：单次尝试成功率、重试/切换率、首数据 P50/P95 耗时、平均输出速度；
- **异常判断**：有效样本数少于 20 个或最近一小时内没有样本时显示“未知”；失败率达到 5% 显示“需关注”，达到 20% 显示“异常”；首数据的 P95 或 P50 超过健康度阈值时也显示“需关注”；停用渠道显示“已停用”；
- **延迟阈值与冷却分离**：健康度用 `HEALTH_SLOW_FIRST_TOKEN_MS`（P95，默认 30 秒）和 `HEALTH_SLOW_P50_FIRST_TOKEN_MS`（P50，默认 10 秒）判定，只产生提示，不触发冷却；冷却仍由 `TTFT_SLOW_THRESHOLD_MS` 与 `TTFT_SLOW_STREAK` 决定。P50 阈值必须不大于 P95，默认值留出足够余量，避免思考型模型把渠道长期压在「需关注」；
- **无可用凭据**：渠道仍启用、但静态密钥与订阅账号里没有任何一条能支持渠道当前模型目录的可路由凭据时显示“无可用凭据”，优先于“未知”判定。该判定只由服务端按完整凭据集给出；报告尚未加载或读取失败时显示“未知”，不用只覆盖静态密钥的本地判定冒充，避免把“账号仍在支撑”的渠道误报为不可用。渠道的启用开关表达运营意图，不代表模型一定可用；两个状态分开显示，避免把“运营者主动关掉”和“想跑但跑不了”混为一谈；
- **明细拆解**：点击渠道可下钻查看按模型、出站协议和具体密钥拆分的成功率与错误原因分布。
- **缓存使用**：展示缓存命中率与缓存读/写、输入 token，并按上游模型拆分各自的命中率（按输入 token 降序），避免不同模型的缓存行为被整体流量摊平；口径与用量报表一致，仅供诊断展示，不参与健康度判定，读取失败不影响健康度统计。按模型拆分的用量来自请求日志，与按上游尝试统计的成功率表口径不同，两者分开展示。

## 六、范围边界

PrismLLM 保持「单实例自托管网关」定位，当前路线图不包含：

- Redis、配置中心或多副本共享状态；
- 渠道/密钥的加权轮换、轮询、HRW/会话亲和或 OAuth 策略重排；模型请求按已保存凭据列表尝试。

配置与每日额度账本持久化于 PostgreSQL，但管理会话、调用方/上游 RPM、并发名额、OAuth 登录/调度与刷新互斥不跨副本共享；候选冷却与部分 OAuth 状态异步快照仅用于重启恢复。本地限流拒绝保持 `429 + Retry-After`，不写入故障冷却。

停机先撤 readiness 并拒绝新数据面准入，再等待在途请求 Drain 与 server/队列清理；默认 Drain 30 秒不是完整停机的绝对上界。Compose 的 gateway 停止预算为 60 秒，增大 `DRAIN_TIMEOUT_MS` 时需同步增大停止预算并保留清理余量，详见 [配置指南](configuration.md)。
