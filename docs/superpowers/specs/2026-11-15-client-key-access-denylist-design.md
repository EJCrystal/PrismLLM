# 调用方密钥访问黑名单设计

状态：用户于 2026-11-15 同意以下三模式方案。

## 目标与约束

调用方密钥的渠道、静态渠道 Key、对外模型 ID 各自选择 `unrestricted`、`allowlist`、`denylist`，同一维度模式互斥，不同维度取交集。白名单只允许所选对象，空白名单拒绝全部；黑名单禁止所选对象，空黑名单不额外限制。新增目标在黑名单模式下按其余规则使用。

模型 ID 精确且区分大小写，无通配符。静态 Key 使用 `(channelId, keyId)` 身份；静态 Key 白名单排除 OAuth，静态 Key 黑名单保留 OAuth。渠道黑名单同时排除该渠道的静态和 OAuth 凭据。

请求、模型列表、搜索、重试、冷却兜底、协议转换及恢复提示共用一次权限快照。未配置模型保持 404，已配置且越权返回既有 403 和稳定错误码。空黑名单与不限制拥有相同的实际授权行为，包括无凭据 503 和旧停用渠道模型口径。

旧不限制和白名单不变。省略或 null 更新保留原权限；完整策略原子替换，轮换和启停保留策略。目标删除不会改变已选模式；模型黑名单 ID 保留，删除并重新配置同 ID 模型仍禁止。静态对象外键级联清理失效 ID，重新创建的对象具有新 ID。

## 方案

已同意：每个维度在三种模式中选择一种，复用现有管理接口 `mode` 与 `ids`/`keys` 格式。另一方案是在同一维度同时维护允许和禁止名单，需要定义冲突优先级并增加界面负担；本版不采用。

## 实现决定

- 领域保留现有三个 nullable allowed 集合，新增三个 nullable denied 集合；null 表示未选择对应模式，非 null 空集合保留该模式。规范化拒绝同维度同时存在两种集合。
- V69 新增三个 denied 模式标记、三个独立黑名单关联表；数据库 CHECK 防止同维度两模式同时启用。旧 V68 不修改。
- 现有批量读取与 REPEATABLE READ 一致快照扩展到黑名单关联；不增加逐密钥查询。
- 管理 API 支持 `denylist`，按对象身份和长度校验。渠道白名单下的静态 Key 黑名单可包含其他现存渠道的 Key，作为无效果的合法排除；静态 Key 白名单必须位于渠道允许范围内。
- 前端复用多选目录，增加黑名单模式及准确摘要。模式切换保留当前名单草稿；由模式决定同一份选择的意义。
- 使用现有 Kotlin/Ktor/Exposed/PostgreSQL/Vue 技术栈，不安装或升级依赖；新增 Kotlin 代码具备标准 KDoc。
