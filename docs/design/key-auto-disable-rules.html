密钥禁用规则：状态码 / 正则 / 临时与永久 / 自动恢复

结论先说：值得做，但只做「错误分类 + 动作 + 能否自动恢复」三件事，不做通用规则引擎。下面每一节都对应现有代码里的一个落点。

一、需不需要丰富规则

需要，但方向不是「让管理员写一堆 if」。现有实现有两个真实问题：

  • 401/403 有两条阈值路径。连续鉴权失败计数和窗口失败计数都会停用密钥，两个门槛对同一类拒绝重复表达，配置项之间没有互补关系。
  • 只认「结果类型」，不认「拒绝原因」。上游用 403 返回「地区不支持」、用 401 返回「模型未开通」时，会和「密钥失效」一起计数，最后停掉一把其实还能用的密钥。
真正缺的是「凭什么判定这把钥匙坏了」。 状态码负责粗筛，错误文本中的稳定特征负责确认，动作决定临时还是永久，恢复策略决定谁来解封。四件事彼此独立，但不需要第 5 件事。
不建议做的事：在管理台暴露任意条规则 + 任意逻辑组合 + 每规则独立窗口。三个参考项目都没有走到那一步，你的渠道是自有 API key，规模也不需要策略编排。

二、三个参考项目怎么做的

sub2api 账号级临时不可调度（temp_unschedulable_until）。规则结构是 error_code + keywords[] + duration_minutes + scope，关键词用小写包含匹配，不启用正则；请求体截断 64 KB、原因截断 2 KB 后入库。401 首次命中先临时停调度给 token 刷新窗口；同一 401 再次命中则升级为账号 error。配额类 429 走另一条路，不击杀账号。
axonhub 规则结构是 statusCodes[] + keywordPatterns[] + times + action，关键词先按正则编译，编译失败退化成大小写不敏感的字面量包含。动作有 temporary_disable、permanent_disable、permanent_disable_delete、disable_until_cron。停用记录带 expiresAt，后台清理任务到期自动恢复；所有 key 都停用后整条渠道一起停用。
CLIProxyAPI 不做「规则表」，做错误分类。ErrorCodeRequestScoped、ErrorCodeConnectionLifecycle、ErrorCodeTransientTransport、ErrorCodeForceCooldown、ErrorCodeTransientRateLimit 这些码决定这次失败该不该算到凭据头上；终态 401 标记为不可调度，且只有 token 变化才解除；429/503 走按模型或按凭据的冷却，冷却到期自动放行探测。

共同点很明确：状态码是主键，文本只做二次确认；临时禁用一定有到期时间；永久禁用一定需要人工处理；恢复要么按时，要么靠一次真实成功。这四条直接照抄，足够了。

三、规则模型

一个密钥健康策略 = 一个全局开关 + 一组有序规则。命中第一条即停止，规则之间不叠加计数。

KeyDisableRule {
  id            string            // 稳定标识，用于审计与计数键
  name          string            // 管理台展示名
  statusCodes   int[]             // 空 = 不按状态码过滤
  bodyPatterns  string[]          // 空 = 不按文本过滤；先试正则，失败退化为字面量
  threshold     int               // 触发阈值，1..1000
  windowMinutes int               // 计数窗口，1..1440
  streak        bool              // true = 连续计数（成功清零）；false = 窗口计数（成功不清零）
  action        Action            // TEMPORARY | PERMANENT
  disableMinutes int?             // TEMPORARY 必填，1..10080
  recovery      Recovery          // NONE | ON_EXPIRY | ON_PROBE
}
为什么保留 streak 和 window 两种 鉴权失效适合「连续」——中间成功一次就说明钥匙是好的。限流和 5xx 适合「窗口」——夹杂成功不代表上游稳定。这正是现有两段配置的真实差异，保留它，但把它从「两个必填阈值」变成「规则自己的属性」。
为什么不做任意条件组合 AND/OR 一出现，管理台就需要表达式编辑器、校验器和解释器，排障时也没人愿意读。规则按顺序匹配、首条命中生效，已经能表达全部真实场景。

匹配与计数语义

  • 只统计真实上游响应。客户端取消、网关本地限流、请求体错误不进入任何规则；请求在首 token 前失败才可能计数。
  • 文本来源是上游错误体。复用 upstreamException 已经解析出的 body（目前只给 Anthropic 原生透传保留），截断后参与匹配，绝不上报给调用方；同一份正文会在失败请求日志中截断脱敏后保存。
  • 正则必须先编译再保存。保存时拒绝非法表达式，而不是运行时静默忽略；限制模式长度 ≤ 200 字符，并只对截断后的错误体匹配。
  • 规则 revision 变更即重新计数。沿用现有 KeyAutoDisableSettings.revision 机制，旧计数作废，不需要迁移历史计数。
  • 只有成功才打断连续计数。未命中任何规则的上游响应（400/404/422）既不计数也不清零；请求参数错误不能证明凭据可用，否则调用方可以用无效请求掩盖一把坏钥匙。
  • 404 默认不参与。模型不存在通常是配置问题，不是钥匙问题；要做也应单独一条规则，明确针对某个上游。

四、默认规则（建议直接内置）

凭据失效永久 · 人工处理

状态码 401 / 403，错误文本命中 invalid_api_key、incorrect api key、authentication_error、invalid_grant，连续 2 次。

上游账号被停永久 · 人工处理

状态码 401 / 403，命中 account.*(disabled|suspended|deactivated)、billing、payment，1 次。

未知鉴权拒绝临时 30 分钟 · 到期自动恢复

状态码 401 / 403，没有命中上面两条，窗口 5 分钟内累计 3 次。

上游不稳定临时 10 分钟 · 到期自动恢复

状态码 429 / 5xx，或传输层失败（连接失败、超时、空流），窗口 5 分钟内累计 8 次。

模型级拒绝不参与禁用

状态码 400 / 404 / 422，只记录日志与冷却，不累计密钥失败。

这套默认值把「真正失效」和「暂时不好用」分开了：前者要求换钥匙，后者等一会儿自己回来。现有默认 3 次 401 永久停用会误杀短期 401（例如 token 轮换窗口），建议按上表调整。

五、禁用之后能不能自动恢复

能，而且必须分两种恢复方式。密钥状态需要从单一 enabled 扩展成明确的状态机：

MANUAL_DISABLED  人工停用          → 只能人工启用
AUTO_TEMPORARY   自动临时禁用      → 到期自动恢复，或探测成功提前恢复
AUTO_PERMANENT   自动永久禁用      → 只能人工换凭据后启用
ACTIVE           正常
临时禁用写到期时间停用与审计在同一事务写 auto_disable_until；请求路径每次选到候选时检查 until > now，过期即视作可用。不依赖定时任务才能恢复，重启也不丢。
后台清理只做收尾复用 GatewayApplication.scope 起一个低频任务（如每 30 秒），把已到期的临时禁用写回 ACTIVE 并清计数；即使任务停了，请求路径的到期判断仍然生效。
到期后用单个探测请求验证和现有候选冷却一致：到期后通过 probe_until 原子抢占探测租约，只放行一个真实请求；成功则恢复并清零健康计数，失败则按命中规则重新计时或转永久停用。这就是 axonhub 的「到期清理」加 CLIProxyAPI 的「探测」。
永久禁用永不自动恢复凭据类错误自动解封只会再撞一次 401，没有意义。管理台必须提供「已换新凭据 → 启用」的显式动作，并保留现有 stateVersion 保护。
人工停用不受自动恢复影响现有代码用 enabled=false 同时表达两种停用，必须拆开，否则清理任务会把管理员主动停掉的密钥重新放出来。这是本方案里最不能省的一处。
触发状态路由是否尝试如何解除

注意：候选冷却已经在做「短时间后置 + 单探测」，不要让新规则把它的职责盖掉。分工是：冷却负责「这个候选现在不好」，自动禁用负责「这把钥匙坏了」。

六、规则试跑

用来验证默认规则是否会把真实错误分错类。改状态码或错误文本，立刻看到命中哪条规则、累计到第几次。逻辑与本方案一致：按顺序首条命中，连续计数成功清零，窗口计数成功不清零。

七、代码落点

规则定义resilience/KeyAutoDisable.kt：把 KeyAutoDisablePolicy 从四个标量换成 rules: List<KeyDisableRule>，record() 返回 (ruleId, matchedPattern, count, action)。纯函数，先把单测写满。
错误体透传api/ProxyRoutes.kt：upstreamException 增加一个仅内部使用的截断错误体字段（如 upstreamErrorBody，最多 8 KB），recordKeyOutcome 把它传给 repository。请求日志会保存同一份正文的截断脱敏副本，避免重复读取响应体。
状态与迁移新增迁移（V32）：channel_keys.state 枚举替换原 enabled 列，新增 auto_disable_until 列。旧数据按 enabled=true → ACTIVE、enabled=false 且 auto_disabled_at 非空 → AUTO_PERMANENT、其余 MANUAL_DISABLED 回填。
计数与停用repo/KeyAutoDisableRepository.kt：按 keyId + ruleId 存计数（现有单行 JSON 可扩展成 map）；停用时写 kind / until / reason；保留行锁与「停用 + 审计同事务」。
路由判断domain/Records.kt#keysFor 与 KeyAutoDisableRepository.isAvailable：把「临时到期」算作可用；候选加载时直接过滤已停用，减少一次无谓的上游尝试。
自动恢复在 GatewayApplication 的 scope 里挂一个低频清理任务，只收尾已到期且没有 probe_until 租约的临时停用；启用时清 ChannelKeyHealth 与 candidateCooldown.clearKey，并写一条 channel_key.auto_recover 审计。
管理面现有 KeyAutoDisableSettingsModal.vue 改成规则列表（可折叠、上移下移、开关），并保留一句人类可读的摘要；API 从 4 个字段改为 rules[]，老字段只读兼容一次。
可观测性指标维度加 rule 与 action：gateway_key_auto_disabled_total{channel,reason,rule,action}、gateway_key_auto_recovered_total{to}。审计详情记录命中规则、模式、计数，不记录完整错误体。
安全边界 正则只用于本地上游错误体，作用在已截断的字符串上；保存时编译校验；单条模式长度上限 200；原始正文不写入应用日志或审计记录；请求日志仅保存截断脱敏后的副本（原生 Messages 与 Gemini 的非 2xx 响应按各协议语义向调用方透传上游错误）。凭据明文仍然只在密文列。

八、实施顺序

第 1 步：纯函数与单测（0.5 天）规则匹配、首条命中、连续 / 窗口计数、revision 失效。此时不碰数据库。
第 2 步：状态与迁移（0.5 天）拆出人工停用 / 自动临时 / 自动永久；回填旧数据；补 auto_disable_until。
第 3 步：接入请求路径（1 天）错误体传递、命中后停用、到期判断、审计与指标。用集成测试覆盖「401 永久」「429 临时」「400 不计数」「客户端取消不计数」。
第 4 步：自动恢复任务（0.5 天）清理任务 + 单探测恢复 + 人工停用不被误恢复的测试。
第 5 步：管理台与文档（1 天）规则列表 UI、规则摘要、ADR 更新、README 的 API 示例。
合计约 3.5 人日。第 1、2 步可独立合并，第 3 步是唯一的危险点：它改动请求路径的停用判断，必须先有集成测试再改。

基于 llm-gateway 当前实现（V31 迁移，含 KeyAutoDisableRepository）与 2026-10-28 拉取的 sub2api / axonhub / CLIProxyAPI 源码整理。
