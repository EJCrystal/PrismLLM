# 候选冷却与档位分摊优先于引入外部路由策略

对照 sub2api、axonhub、CLIProxyAPI 的路由策略后，不整建制接入任何外部方案，只针对两个真实动机各做一个机制：可靠性——候选冷却；成本——档位分摊。两者都实现为候选发现后的过滤与排序步骤，不抽 Router/Strategy 接口。

**候选冷却**：冷却按（渠道，上游模型）候选记录。触发规则按渠道凭证类型参数化：瞬时错误（连接失败、超时、空流、5xx）30 秒起步、同候选连续失败翻倍、封顶 10 分钟；429 遵从 `Retry-After`、封顶 60 秒；401/403 长冷却 10 分钟并打 ERROR 日志，不自动禁用渠道；404 不冷却；流式请求首 token 连续 3 次超过软阈值（默认 10 秒）视同瞬时错误，被计数的请求本身照常服务，非流式不计数。冷却只后置不禁用：优先尝试未冷却候选，全部候选都在冷却中时仍按档位顺序照常尝试（fail-open）。状态内存为准，变更异步写透 PostgreSQL，启动时加载，重启不丢。

**档位分摊**：`alias_candidates.position` 从严格全序升级为优先级档位，同档内轮询分摊流量，失败或冷却才落到下一档；分摊发生在同一对外模型 ID 的候选之间。直连候选同处一档、天然参与分摊，渠道名字典序不再决定顺序。权重留作档内未来字段（默认 1）。

## 理由

三个开源项目的路由复杂度大多由订阅账号池场景塑造（封号摘除、token 刷新池、错误体正则分类），本网关渠道是自有 API key 上游，照搬是死重；axonhub 式多策略打分是渠道多到管理员排不过来的规模才需要的东西。两个动机各有归属：渠道故障后每个请求白撞一次失败、摘渠道靠人工，是可靠性痛点；部分渠道有优惠或福利、需要把流量摊过去，是成本动机。冷却只后置不禁用，因为冷却是启发式不是事实——宁可多撞一次失败，也不把实际可用的服务拒之门外；而状态写透数据库只在状态翻转时发生，不增加数据面每请求延迟，换来重启不必重新撞失败。档位制同时保住主备语义（档间）与分摊（档内），比让管理员拍权重数字直观；首 token 软阈值是冷却的最小健康感知形式——硬超时负责"卡死就切"，软阈值负责"持续变慢就绕开"。

## Consequences

明确不做：权重分摊、fill-first、会话粘性、渠道级限流、健康评分排序（首 token 软阈值这种简单形式除外）、管理端冷却 UI。冷却事件通过日志与 Prometheus 指标观测；冷却参数走环境变量。冷却触发规则按渠道凭证类型参数化，为规划中的订阅账号预留：届时账号池数据模型（订阅账号=渠道新类型，或渠道下挂账号池）需另行 ADR，并修订 CONTEXT.md 渠道词条（现列为 Avoid"账号"）；会话粘性与渠道级限流集中到订阅里程碑重估；Router/Strategy 接口与策略配置化推迟到账号池轮换真正落地时再抽。
