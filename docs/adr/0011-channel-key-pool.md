# 渠道密钥池与密钥级路由

渠道从“一个渠道一个上游凭据”扩展为“一个渠道下挂多个上游密钥”。密钥拥有独立的凭据、启用状态、优先级和可用模型集合。当前模型请求由每个公共模型 ID 显式保存的有序凭据身份列表决定顺序；优先级仅为兼容性字段，不参与运行时排序。渠道仍是一个供应商接入点，`baseUrl`、协议、对外模型 ID 和模型价格保持在渠道级；鉴权保留渠道级 `authType` 默认值，并允许通过 `protocolAuthTypes` 按出站协议覆盖。

## 边界

- 同一渠道的所有密钥共用 `baseUrl`、渠道级默认 `authType`、协议覆盖和 `protocols`。不同基础地址必须拆成不同渠道；同一接入点的不同出站协议可通过 `protocolAuthTypes` 分别选择鉴权方式。协议覆盖对渠道内所有密钥生效，不能区分同一协议下不同密钥的鉴权方式；若这些密钥在同一协议下需要不同鉴权方式，仍须拆分渠道。
- 对外模型 ID 与模型价格保持在渠道级。同一上游模型不允许在不同密钥上映射到不同的对外 ID 或价格。
- 渠道、静态密钥和 OAuth 账号的 `priority` API/存储字段继续保留，范围仍为 `1..1000`、默认值为 `1`，但不影响模型请求顺序。模型路由是全序列表，原生/转换协议、优先级、轮询、HRW 和 OAuth 排序策略都不能重排。
- 一个密钥可以支持多个模型；多个密钥可以支持同一个模型。后者是容量池，不是故障别名。
- 渠道的模型目录是所有密钥模型集合的并集；密钥只能使用渠道目录中的模型。

## 数据模型

- `channel_keys`：密钥 id、所属渠道、名称、加密凭据、启用状态、优先级和时间戳。
- `channel_key_models`：密钥 id 与上游模型名，表示该密钥可以调用哪些模型。
- `channel_key_rate_limits`：密钥 id、启用状态、每分钟请求数和最大并发请求数；无记录表示不限流。
- `channel_models` 继续保存渠道级模型目录及对外模型 ID 映射。
- `request_logs` 增加 `channel_key_id` 和 `channel_key_name` 快照，用于区分同一渠道内的实际服务密钥。
- 现有渠道迁移为一个名为“默认密钥”的密钥，原凭据和模型授权完整复制。

## 路由

请求使用对外模型 ID（Canonical ID）读取已保存路由，每个条目只包含 `channelId`、`credentialType`（`static` 或 `oauth`）和 `credentialId`。身份列表决定外层顺序，渠道与模型目录只用于展开别名和检查资格。

- 严格按列表尝试符合资格的身份，转换候选可以位于原生候选之前；不按渠道或凭据优先级、轮询、HRW/亲和及 OAuth 策略重排。
- 同一凭据的多个上游模型名映射到同一对外模型 ID 时，保持连续稳定的主入口/回退顺序，不把不同凭据按上游模型名重新合池。
- `prompt_cache_key` 仅作为请求字段转发，不影响路由顺序。`OAUTH_ROUTING` 已弃用；旧值仍能读取，但没有运行时排序效果。
- 渠道启停、静态凭据状态、OAuth 鉴权状态/启用状态、目录与模型授权、调用方授权、额度、窗口及并发资格继续生效。响应提交前发生可重试失败时只尝试列表内后续候选，响应提交后不切换。
- 未配置模型路由时管理面返回 `configured=false`、revision `0`、空 `entries`，数据面不做候选发现回退；显式保存 `entries: []` 表示停止该模型的路由。
- V73 只对升级时的当前模型做一次性 seed，初始条目仅包含当时已启用且符合模型/账号资格的凭据。之后新增模型或凭据必须由管理员显式选入，不会自动追加。

管理员可在「模型路由」中显式保存例如 A 福利 → B 福利 → A 普通 → B 普通的顺序；这个顺序来自列表本身，与 `priority` 数值或成本无关。接口及冷却边界见 [路由与容灾机制](../routing-and-resilience.md)。

## 冷却

冷却键按影响面拆分：

- 连接失败、超时和 5xx 记渠道键，冷却整个渠道。
- 401/403 记密钥键，只冷却具体密钥，不连坐同渠道其他密钥。
- 429 和首 token 持续过慢记“密钥 + 上游模型”键，不连坐同密钥的其他模型。
- 404 不冷却。

所有已配置路由候选都在冷却或探测中时仍保持 fail-open，但只按已保存列表尝试，不补入未选凭据。

## 自动禁用扩展（2026-10-28）

在原有冷却之上增加每个上游密钥独立的自动禁用门槛。规则按顺序匹配、首条命中生效：401/402/403 且命中 `INSUFFICIENT_BALANCE` 1 次即永久停用；401/403 且命中 `invalid_api_key` 等稳定特征连续 2 次永久停用；账号停用或其他结算类 1 次永久停用；其余 401/403 在 5 分钟内 3 次临时停用 30 分钟；429/5xx/连接失败/超时在 5 分钟内 8 次临时停用 10 分钟。成功只清零连续计数，窗口计数保留；400/404/422 不命中规则、不计数。密钥处于冷却时仍可按既有 fail-open 规则探测，但已停用密钥永不参与 fail-open。

规则列表保存在 `key_auto_disable_settings.rules`，按规则分桶的失败计数保存在 `channel_key_health.rule_counters`；管理台提供 `GET/PUT /admin/api/key-auto-disable-settings`。计数按密钥行锁串行处理，跨模型、协议和进程共享；规则变更通过 revision 使旧计数失效。停用与 `channel_key.auto_disable` 系统审计在同一事务提交。审计详情记录命中规则、渠道/密钥名称、计数、动作、状态、到期时间及上游状态，不落凭据或请求正文。

`channel_keys.state_version` 保护旧请求和旧编辑表单：更换凭据或启用状态变更后，旧请求不会影响新状态，携带旧 `stateVersion` 的编辑请求得到 409。永久自动禁用的密钥可由管理员人工启用，凭据可保留或替换；恢复时清零失败计数并清除密钥级冷却。已停用的密钥不会因关闭规则自动恢复。

### 状态机与四态扩展（V32 迁移）

`channel_keys.enabled` 布尔列升级为单一 `state` 枚举列（`ACTIVE`、`MANUAL_DISABLED`、`AUTO_TEMPORARY`、`AUTO_PERMANENT`），并新增 `auto_disable_until` 字段：
- `ACTIVE`：正常可用。
- `MANUAL_DISABLED`：管理员人工停用，永不被系统自动恢复改写；人工启用无需换凭据。
- `AUTO_TEMPORARY`：规则触发的临时停用，带有到期时间 `auto_disable_until`；读路径与路由层到期即自动视作可用，不依赖后台任务。
- `AUTO_PERMANENT`：严重错误触发的永久停用，无到期时间；不会自动恢复，管理员人工启用后可保留或替换上游凭据。
V32 迁移自动按 `enabled` 和历史 `auto_disabled_at` 回填旧数据并删除 `enabled` 列。API 层面请求与响应均切换为 `state`，客户端只能显式提交 `ACTIVE` 或 `MANUAL_DISABLED`。

## 上游分组主动限流（2026-10-28）

每个密钥只代表一个上游分组，因此主动限流不增加“适用模型”维度。RPM 和最大并发统一按 `channelId + keyId` 计数，覆盖该密钥支持的全部模型；未配置或关闭规则时不消耗额度。RPM 使用单实例内存令牌桶，最大并发以实际发送上游请求为边界持有租约，并在成功、失败、超时和取消时释放。

本地主动限流与上游错误处理分离：拒绝当前密钥时继续尝试其他候选；全部候选均被本地限流时返回 `429 upstream_key_rate_limit_exceeded` 和 `Retry-After`，不写入冷却，也不计入自动禁用失败。规则持久化在 `channel_key_rate_limits`，管理台按密钥编辑，未配置是默认状态。

## 管理面

- 渠道编辑页以密钥卡片管理密钥：名称、兼容性优先级、启用状态、凭据和可用模型。
- 「模型路由」独立管理每个公共模型的有序凭据列表，通过 `GET /admin/api/model-routes?q=&offset=&limit=`、`GET /admin/api/model-routes/detail?modelId=` 与 `PUT /admin/api/model-routes` 读写；保存提交 `modelId`、`expectedRevision` 和仅含身份的 `entries`。
- 模型发现、协议探测和连通性测试支持显式指定凭据；管理操作的默认凭据选择不改变数据面已保存路由。
- 旧版单凭据请求仍兼容：新建时自动生成“默认密钥”，更新时只作用于唯一的默认密钥。渠道存在多个密钥时，旧版请求必须显式提交密钥列表。

## 不在本次范围

- 密钥级价格、调用方额度和健康评分。
- 密钥级协议、鉴权或基础地址。
- 别名直接绑定具体密钥。
- 密钥级管理端冷却状态面板。

## 理由

把密钥放在渠道下，可以复用渠道的供应商配置、模型目录和价格，同时让多个凭据组成容量与容灾池；实际模型顺序由管理员的显式列表决定。若把每个密钥建成独立渠道，会重复模型映射、价格和别名配置，也无法表达“同一供应商接入点下的密钥池”。

## Consequences

路由候选从 `(渠道, 上游模型)` 变为 `(渠道, 密钥, 上游模型)`，冷却状态、请求日志、模型测试和管理界面都需要感知密钥维度。旧的单凭据渠道在迁移后仍按原数据工作；数据面尝试顺序由模型路由显式保存。
