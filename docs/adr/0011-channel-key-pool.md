# 渠道密钥池与密钥级路由

渠道从“一个渠道一个上游凭据”扩展为“一个渠道下挂多个上游密钥”。密钥拥有独立的凭据、启用状态、优先级和可用模型集合；同一渠道内的多个密钥按密钥优先级分档，同档轮询。渠道仍是一个供应商接入点，`baseUrl`、鉴权方式、协议、对外模型 ID 和模型价格保持在渠道级。

## 边界

- 同一渠道的所有密钥共用 `baseUrl`、`authType` 和 `protocols`。不同基础地址、鉴权方式或协议必须拆成不同渠道。
- 对外模型 ID 与模型价格保持在渠道级。同一上游模型不允许在不同密钥上映射到不同的对外 ID 或价格。
- 密钥优先级只在渠道内生效；跨渠道仍先按渠道优先级分档。
- 一个密钥可以支持多个模型；多个密钥可以支持同一个模型。后者是容量池，不是故障别名。
- 渠道的模型目录是所有密钥模型集合的并集；密钥只能使用渠道目录中的模型。

## 数据模型

- `channel_keys`：密钥 id、所属渠道、名称、加密凭据、启用状态、优先级和时间戳。
- `channel_key_models`：密钥 id 与上游模型名，表示该密钥可以调用哪些模型。
- `channel_models` 继续保存渠道级模型目录及对外模型 ID 映射。
- `request_logs` 增加 `channel_key_id` 和 `channel_key_name` 快照，用于区分同一渠道内的实际服务密钥。
- 现有渠道迁移为一个名为“默认密钥”的密钥，原凭据和模型授权完整复制。

## 路由

请求模型先按协议和渠道模型目录筛出候选渠道，再在渠道内筛出支持该模型的启用密钥。

- 渠道之间按渠道优先级分档；同档渠道轮询。
- 渠道内按密钥优先级分档；同档密钥轮询，低优先级密钥只在高优先级密钥失败或冷却时启用。
- 同一渠道内多个上游模型映射到同一个对外模型 ID 时，保留现有的主入口/回退语义：先尝试主上游模型下的密钥池，全部失败或冷却后再尝试下一个上游模型。
- 首 token 前失败可以继续尝试同渠道的其他密钥，再尝试下一个渠道；首 token 后不切换。

## 冷却

冷却键按影响面拆分：

- 连接失败、超时和 5xx 记渠道键，冷却整个渠道。
- 401/403 记密钥键，只冷却具体密钥，不连坐同渠道其他密钥。
- 429 和首 token 持续过慢记“密钥 + 上游模型”键，不连坐同密钥的其他模型。
- 404 不冷却。

所有候选都在冷却或探测中时仍保持 fail-open，按档位顺序照常尝试。

## 管理面

- 渠道编辑页以密钥卡片管理密钥：名称、优先级、启用状态、凭据和可用模型。
- 模型发现、协议探测和连通性测试支持指定密钥；未指定时使用该模型下优先级最高的启用密钥。
- 旧版单凭据请求仍兼容：新建时自动生成“默认密钥”，更新时只作用于唯一的默认密钥。渠道存在多个密钥时，旧版请求必须显式提交密钥列表。

## 不在本次范围

- 密钥级价格、配额、限流和健康评分。
- 密钥级协议或基础地址。
- 别名直接绑定具体密钥。
- 密钥级管理端冷却状态面板。

## 理由

把密钥放在渠道下，可以复用渠道的供应商配置、模型目录和价格，同时让多个账号或 API key 按优先级分摊容量。若把每个密钥建成独立渠道，会重复模型映射、价格和别名配置，也无法表达“同一供应商接入点下的密钥池”。

## Consequences

路由候选从 `(渠道, 上游模型)` 变为 `(渠道, 密钥, 上游模型)`，冷却状态、请求日志、模型测试和管理界面都需要感知密钥维度。旧的单凭据渠道在迁移后仍按原行为工作，但新功能只对显式配置的密钥池生效。
