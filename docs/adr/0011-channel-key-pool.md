# 渠道密钥池与密钥级路由

渠道从“一个渠道一个上游凭据”扩展为“一个渠道下挂多个上游密钥”。密钥拥有独立的凭据、启用状态、优先级和可用模型集合；同一渠道内的多个密钥按密钥优先级分档，同档轮询。渠道仍是一个供应商接入点，`baseUrl`、鉴权方式、协议、对外模型 ID 和模型价格保持在渠道级。

## 边界

- 同一渠道的所有密钥共用 `baseUrl`、`authType` 和 `protocols`。不同基础地址、鉴权方式或协议必须拆成不同渠道。
- 对外模型 ID 与模型价格保持在渠道级。同一上游模型不允许在不同密钥上映射到不同的对外 ID 或价格。
- 密钥优先级只在渠道内生效；跨渠道仍先按渠道优先级分档。
- 一个密钥可以支持多个模型；多个密钥可以支持同一个模型。后者是容量池，不是故障别名。
- 渠道的模型目录是所有密钥模型集合的并集；密钥只能使用渠道目录中的模型。

## 数据模型

- `channel_keys`：密钥 id、所属渠道、名称、加密凭据、启用状态、优先级和时间戳。
- `channel_key_models`：密钥 id 与上游模型名，表示该密钥可以调用哪些模型。
- `channel_key_rate_limits`：密钥 id、启用状态、每分钟请求数和最大并发请求数；无记录表示不限流。
- `channel_models` 继续保存渠道级模型目录及对外模型 ID 映射。
- `request_logs` 增加 `channel_key_id` 和 `channel_key_name` 快照，用于区分同一渠道内的实际服务密钥。
- 现有渠道迁移为一个名为“默认密钥”的密钥，原凭据和模型授权完整复制。

## 路由

请求模型先按协议和渠道模型目录筛出候选渠道，再在渠道内筛出支持该模型的启用密钥。

- 渠道之间按渠道优先级分档；同档渠道轮询。
- 渠道内按密钥优先级分档；同档密钥轮询，低优先级密钥只在高优先级密钥失败或冷却时启用。
- 同一渠道内多个上游模型映射到同一个对外模型 ID 时，保留现有的主入口/回退语义：先尝试主上游模型下的密钥池，全部失败或冷却后再尝试下一个上游模型。
- 首 token 前失败可以继续尝试同渠道的其他密钥，再尝试下一个渠道；首 token 后不切换。

## 冷却

冷却键按影响面拆分：

- 连接失败、超时和 5xx 记渠道键，冷却整个渠道。
- 401/403 记密钥键，只冷却具体密钥，不连坐同渠道其他密钥。
- 429 和首 token 持续过慢记“密钥 + 上游模型”键，不连坐同密钥的其他模型。
- 404 不冷却。

所有候选都在冷却或探测中时仍保持 fail-open，按档位顺序照常尝试。

## 自动禁用扩展（2026-10-28）

在原有冷却之上增加每个上游密钥独立的自动禁用门槛。规则按顺序匹配、首条命中生效：401/403 且命中 `invalid_api_key` 等稳定特征连续 2 次永久停用；账号停用或结算类 1 次永久停用；其余 401/403 在 5 分钟内 3 次临时停用 30 分钟；429/5xx/连接失败/超时在 5 分钟内 8 次临时停用 10 分钟。成功只清零连续计数，窗口计数保留；400/404/422 不命中规则、不计数。密钥处于冷却时仍可按既有 fail-open 规则探测，但已停用密钥永不参与 fail-open。

规则列表保存在 `key_auto_disable_settings.rules`，按规则分桶的失败计数保存在 `channel_key_health.rule_counters`；管理台提供 `GET/PUT /admin/api/key-auto-disable-settings`。计数按密钥行锁串行处理，跨模型、协议和进程共享；规则变更通过 revision 使旧计数失效。停用与 `channel_key.auto_disable` 系统审计在同一事务提交。审计详情记录命中规则、渠道/密钥名称、计数、动作、状态、到期时间及上游状态，不落凭据或请求正文。

`channel_keys.state_version` 保护旧请求和旧编辑表单：更换凭据或启用状态变更后，旧请求不会影响新状态，携带旧 `stateVersion` 的编辑请求得到 409。手动启用自动禁用的密钥必须更换凭据，恢复时清零失败计数并清除密钥级冷却；已停用的密钥不会因关闭规则自动恢复。

### 状态机与四态扩展（V32 迁移）

`channel_keys.enabled` 布尔列升级为单一 `state` 枚举列（`ACTIVE`、`MANUAL_DISABLED`、`AUTO_TEMPORARY`、`AUTO_PERMANENT`），并新增 `auto_disable_until` 字段：
- `ACTIVE`：正常可用。
- `MANUAL_DISABLED`：管理员人工停用，永不被系统自动恢复改写；人工启用无需换凭据。
- `AUTO_TEMPORARY`：规则触发的临时停用，带有到期时间 `auto_disable_until`；读路径与路由层到期即自动视作可用，不依赖后台任务。
- `AUTO_PERMANENT`：凭据失效等严重错误触发的永久停用，无到期时间；必须更换上游凭据后方可重新启用。
V32 迁移自动按 `enabled` 和历史 `auto_disabled_at` 回填旧数据并删除 `enabled` 列。API 层面请求与响应均切换为 `state`，客户端只能显式提交 `ACTIVE` 或 `MANUAL_DISABLED`。

## 上游分组主动限流（2026-10-28）

每个密钥只代表一个上游分组，因此主动限流不增加“适用模型”维度。RPM 和最大并发统一按 `channelId + keyId` 计数，覆盖该密钥支持的全部模型；未配置或关闭规则时不消耗额度。RPM 使用单实例内存令牌桶，最大并发以实际发送上游请求为边界持有租约，并在成功、失败、超时和取消时释放。

本地主动限流与上游错误处理分离：拒绝当前密钥时继续尝试其他候选；全部候选均被本地限流时返回 `429 upstream_key_rate_limit_exceeded` 和 `Retry-After`，不写入冷却，也不计入自动禁用失败。规则持久化在 `channel_key_rate_limits`，管理台按密钥编辑，未配置是默认状态。

## 管理面

- 渠道编辑页以密钥卡片管理密钥：名称、优先级、启用状态、凭据和可用模型。
- 模型发现、协议探测和连通性测试支持指定密钥；未指定时使用该模型下优先级最高的启用密钥。
- 旧版单凭据请求仍兼容：新建时自动生成“默认密钥”，更新时只作用于唯一的默认密钥。渠道存在多个密钥时，旧版请求必须显式提交密钥列表。

## 不在本次范围

- 密钥级价格、调用方额度和健康评分。
- 密钥级协议或基础地址。
- 别名直接绑定具体密钥。
- 密钥级管理端冷却状态面板。

## 理由

把密钥放在渠道下，可以复用渠道的供应商配置、模型目录和价格，同时让多个账号或 API key 按优先级分摊容量。若把每个密钥建成独立渠道，会重复模型映射、价格和别名配置，也无法表达“同一供应商接入点下的密钥池”。

## Consequences

路由候选从 `(渠道, 上游模型)` 变为 `(渠道, 密钥, 上游模型)`，冷却状态、请求日志、模型测试和管理界面都需要感知密钥维度。旧的单凭据渠道在迁移后仍按原行为工作，但新功能只对显式配置的密钥池生效。
